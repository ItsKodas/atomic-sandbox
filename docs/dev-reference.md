## Releasing

A release is built by GitHub Actions from a pushed tag (`.github/workflows/release.yml`; installer spec `docs/superpowers/specs/2026-11-12-installer-updater-design.md`, plan Task 6) and comes out as a **draft**. Claude never pushes a tag or publishes a release without asking the user first, and never handles the signing secret.

- **Tags.** `vX.Y.Z` is a release (the Stable channel); `vX.Y.Z-beta.N` is a pre-release (the Beta channel; the workflow marks it pre-release on GitHub). The tag without its `v` must equal the root `Cargo.toml`'s `[workspace.package] version`, or the workflow fails before it builds. Bump that version in a commit of its own, with the `Cargo.lock` the next `cargo build` writes (CI builds `--locked`, so a stale lock fails). The app's own version is `CARGO_PKG_VERSION`.
- **The workflow.** Three jobs. **build** (`windows-latest`, token `contents: read`, every run; it references no secret): the tag check; for a pushed tag, it fails at once while `crates/app/release-key.pub` is the placeholder; `cargo build -p app --release --locked`; Inno Setup **6.6.1**, a pinned download checked against its SHA-256 (the runner image's Inno Setup is never used); `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\package.ps1 -RequireInstaller` (the same layout `build.bat` makes, committed files only); `SHA256SUMS.txt` over the installer and the zip (`<sha256>  <name>`, LF); `AtomicSandbox.exe --write-manifest dist\manifest.json` (through `Start-Process -Wait`: a windowed exe) with each asset's name, size and sha256 filled in; the files kept as a workflow artifact for 7 days, and for a pushed tag `SHA256SUMS.txt` alone in an artifact of its own. **sign** (pushed tags only, `github.event_name == 'push' && github.ref_type == 'tag'`; `windows-latest`, no repository token, in the GitHub Environment **`release`**, which holds the two signing secrets, lets only `v[0-9]*` tags deploy and waits for its required reviewer): minisign **0.12** (pinned download, SHA-256 checked); it downloads only `SHA256SUMS.txt`, checks it lists exactly this version's installer and zip, signs it with `minisign -S -H -t "atomic-sandbox <tag>"` (prehashed: the app's `verify` refuses legacy signatures; the trusted comment ties the signature to its release — the app refuses a signature whose trusted comment isn't `atomic-sandbox <the tag it installs>`, `update::verify::trusted_comment_for`, so a signature can't be replayed onto another release's sums) and uploads the `.minisig`. It never checks out or builds repository code. **release** (pushed tags only, `windows-latest`, `contents: write`, never sees a secret): `minisign -V -H` against the tagged commit's `release-key.pub` (a secret that isn't that key's pair fails the run), the trusted comment, the sums against the files, `manifest.json` against the tag and the files (its version, and each asset's name, size and sha256); then, unless `gh release view <tag>` already finds a release for the tag (it stops: "a release for <tag> already exists — delete the stale draft first", e.g. after a create that failed part-way), `gh release create <tag> --draft --verify-tag --title "Atomic Sandbox <ver>"` (plus `--prerelease` for `-beta.N`) with the installer, the zip, `SHA256SUMS.txt`, `SHA256SUMS.txt.minisig` and `manifest.json`. The notes say how to install, the SmartScreen line ("Windows may show 'Windows protected your PC' — the installer isn't code-signed yet: More info → Run anyway."), and that the physics suites were run locally on the tagged commit — true only once the checklist below is done, which is why the release stays a draft until then.
- **Build-only runs.** `workflow_dispatch` (Actions ▸ Release ▸ Run workflow; on any ref, a tag included) runs the build job alone, the installer compile included. It never signs, never sees a secret (the secrets exist only in the `release` Environment, which a branch can't deploy to) and never creates a release; download the files from the run's artifact (7 days). Its `SHA256SUMS.txt` is unsigned, so the app would refuse to install from it. The only other trigger is a pushed `v*` tag. (A push to the `installer` branch was build-only too, for the installer's first compile before any tag; it was removed in that branch's final merge.)
- **The one-time setup: the tag ruleset, the `release` Environment, the signing key and its secrets (the user, not Claude).** Install minisign (`winget install jedisct1.minisign`) and sign in to `gh` (`gh auth login`). Do the steps in this order: the ruleset and the Environment, with their rules, come before the secrets. A job that names a missing Environment creates it with no protection, and a secret added before the rules would be unguarded until they exist. The signing secrets must exist **only** as secrets of the `release` Environment, never as repository secrets: an Environment secret silently shadows a repository secret of the same name, so the workflow can't tell, and a repository secret is readable by any run on any branch. Run the `gh api` steps in Git Bash (they need its quoting), and the steps marked **cmd** in cmd.exe or Windows Terminal: under Git Bash's mintty, `gh` can't see a terminal and reads the password from stdin to its end with no prompt, and minisign can't hide what is typed. Work at the repository root, where both key files are git-ignored.
  1. **The tag ruleset** (Git Bash). A pushed release tag (`v[0-9]*`) can't be moved or deleted, by anyone, admins included (no bypass actors):

     ```bash
     echo '{"name":"release tags","target":"tag","enforcement":"active","bypass_actors":[],"conditions":{"ref_name":{"include":["refs/tags/v[0-9]*"],"exclude":[]}},"rules":[{"type":"update"},{"type":"deletion"}]}' | gh api --method POST repos/ItsKodas/atomic-sandbox/rulesets --input -
     ```

     Or on GitHub: the repository's **Settings ▸ Rules ▸ Rulesets ▸ New ruleset ▸ New tag ruleset**: name `release tags`, **Enforcement status: Active**, leave the **Bypass list** empty, **Target tags ▸ Add target ▸ Include by pattern** `v[0-9]*`, tick **Restrict updates** and **Restrict deletions**, **Create**. Creating a `v*` tag stays open to anyone with write access (only you). A tag pushed on the wrong commit is then fixed with the next version number, not by moving the tag. To move or delete one regardless, disable the ruleset first: a deliberate act.
  2. **The Environment `release`** (Git Bash): you as required reviewer, admins unable to bypass it, and deployments only from tags matching the same `v[0-9]*`:

     ```bash
     printf '{"reviewers":[{"type":"User","id":%s}],"can_admins_bypass":false,"deployment_branch_policy":{"protected_branches":false,"custom_branch_policies":true}}' "$(gh api users/ItsKodas --jq .id)" | gh api --method PUT repos/ItsKodas/atomic-sandbox/environments/release --input -
     gh api --method POST repos/ItsKodas/atomic-sandbox/environments/release/deployment-branch-policies -f name='v[0-9]*' -f type=tag
     gh api repos/ItsKodas/atomic-sandbox/environments/release --jq '{reviewers: [.protection_rules[].reviewers[]?.reviewer.login], can_admins_bypass, policy: .deployment_branch_policy}'
     gh api repos/ItsKodas/atomic-sandbox/environments/release/deployment-branch-policies --jq '.branch_policies[] | {name, type}'
     ```

     The last two print what was set: your login, `false`, custom policies, and `v[0-9]*` of type `tag`. Or on GitHub: **Settings ▸ Environments ▸ New environment**, name `release`, **Configure environment**:
     - tick **Required reviewers** and add yourself (leave **Prevent self-review** unticked: you push the tag and approve it);
     - untick **Allow administrators to bypass configured protection rules**;
     - under **Deployment branches and tags** choose **Selected branches and tags ▸ Add deployment branch or tag rule**, **Ref type: Tag**, pattern `v[0-9]*`, **Add rule**;
     - **Save protection rules**.
  3. **The key pair** (**cmd**). It asks for a password twice; keep it:

     ```bat
     minisign -G -p release-key.pub -s release-key.sec
     ```

  4. **The two secrets, on the Environment** (**cmd**; `--env release` on both). The second asks for the key's password and stores it:

     ```bat
     gh secret set MINISIGN_SECRET_KEY --env release < release-key.sec
     ```

     ```bat
     gh secret set MINISIGN_PASSWORD --env release
     ```

     Or on GitHub: **Settings ▸ Environments ▸ release ▸ Environment secrets ▸ Add environment secret**, `MINISIGN_SECRET_KEY` with the whole of `release-key.sec` (both lines), then `MINISIGN_PASSWORD`. Then check that `gh secret list --env release` shows both, and that `gh secret list` (the repository's own secrets) shows neither. If it does, delete them there: `gh secret delete MINISIGN_SECRET_KEY` and `gh secret delete MINISIGN_PASSWORD`, with no `--env`.
  5. **The public key.** Copy `release-key.pub` into `crates/app/release-key.pub` (`copy /y release-key.pub crates\app\release-key.pub`). It must hold exactly minisign's two lines, `untrusted comment: …` then the `RW…` key, and nothing else: no `#` comment or blank line. The app would skip those, but the release job's `minisign -V -p` would fail on them, late. Replace the test `update::verify::tests::placeholder_key_installs_nothing` as its doc comment says, and commit both (the user, or Claude on the user's word).
  6. **The secret key file.** Move `release-key.sec` out of the repository to a safe backup. It never enters the repo. Losing it means a new key, after which installed builds can't verify a release until they are reinstalled by hand from a build carrying the new key.
- **The checklist, per release.**
  1. On the commit to tag (the version bump merged to `main`), run the gates locally: `cargo test -p units -p qm -p sim -p surrogate --release`, `cargo test -p providers --release`, `cargo test -p validate --release` and `cargo test -p app --release` (one heavy job at a time; the runner has no GPU, so these never run in CI).
  2. Check the README and `DEVLOG.md` are current, and whether `SCENE_FORMAT` or `PROFILE_FORMAT` needs a bump (below).
  3. **Ask the user**, then push the tag: `git tag vX.Y.Z` and `git push origin vX.Y.Z` (the tag alone, never `--tags`).
  4. Wait for the build, then approve the **sign** job's deployment to `release` (Actions ▸ the run ▸ **Review deployments**; the job waits until then). **Approve only the run for the tag you just pushed**: its ref is that tag, and its commit is the one you tagged on `main`. Reject any other. Then check the draft on GitHub: the five assets, the title, the pre-release mark for a beta, the notes. Optionally install the draft's installer by hand.
  5. **Ask the user**, then publish the draft (on GitHub, or `gh release edit vX.Y.Z --draft=false`). The app's updater sees only published releases.
- **When to bump `SCENE_FORMAT` and `PROFILE_FORMAT`.** These two are code-only numbers (scene files and profiles carry no version line, because an older parser refuses unknown lines), recorded in each release's `manifest.json` under `formats`, so a downgrade across a bump warns by type. Bump `crate::scene::SCENE_FORMAT` (`crates/app/src/scene.rs`) when a scene file this build writes would not parse in the previous release, or would mean something else there: a new line or field, a changed meaning or unit. Adding a reader for an older form does not bump it. Bump `crate::ui::profile::PROFILE_FORMAT` (`crates/app/src/ui/profile.rs`) when a profile this build writes would lose or change settings in the previous release: a renamed or re-meant key, a changed value grammar (`layout`, `hidden`, `window`). A new key alone does not bump it, since older builds skip unknown keys. Every other format number (`collection`, `sidecar`, `history`, `replay`, `pseudo_cache`, `checkpoint`) is read from its real version constant (`app::update::formats`) and moves only when that constant does. So a new persisted code or field inside an existing format (a new quarantine code in the sidecar, a new record field in a collection) needs that format's version bumped too, or the downgrade warnings can't see it.
- **Hidden flags** (for the installer and the release workflow, not for users):
  - `--write-manifest <path>`: writes this build's `manifest.json` (version, channel, data formats, no assets; `update::write_manifest`) and exits. The release workflow runs it on the shipped exe and fills in the assets.
  - `--write-icon <path>`: writes the app's `.ico` (the one `build.rs` embeds) and exits; `scripts\package.ps1` uses it for the installer's own icon.
  - `--resume-session <file>`: the installer's relaunch after an update. Opens the session scene saved before the hand-off (`<root>\updates\session.scene`, `update::apply::Session`) paused, in the window only.
  - `--update-failed`: added by the installer when a silent update got past its wait but failed; the status line says the installed files may be mixed (`main::UPDATE_FAILED`).

## Open-shell model: body-4 degree, no ratchet, local misfit (2026-11-14)

- Spec `docs/superpowers/specs/2026-11-13-open-shell-model-design.md` (with its §4.3 amendment), plan `docs/superpowers/plans/2026-11-13-open-shell-model.md`; record in `crates/validate/references.md` "Refit cost at body-4 degree 3", "Local misfit" and "Acceptance (2026-11-14 …)".
- **Body-4 degree (G1).** `Basis::body4_degree`, recorded per basis; `surrogate::descriptor::BODY4_DEGREE_CAP` (3) is the ceiling, `BODY4_DEGREE_START` (2) the start. `providers::surrogate` `grown_body4_degree` steps up when fitted ≥ the degree-3 `Samples` floor + `MIN_RESIDUAL_DOF` (30) and steps down only below that floor. A sidecar written at 2 loads and answers at 2 (`body4_cap`); the degree is part of the background refit's "something other than new data changed" check and of the Model tab's fit line (`last_fit_line`).
- **No ratchet (G2).** `recover_trust` (quarantine.rs) — main's leave-one-out ranking with its training-residual fallback, then step 3 when not recovered — keeps a result only if it ends trusted (short of the counts, only if it passes the residuals and the noise); otherwise it restores the entry fit, quarantine codes, degree cap and persisted codes (`Q_FORGOTTEN` untouched). Notes `RECOVERY_FAILED_NOTE` and the settled note (`settle_recovery_note`, from `refit_inner` and `set_policy`).
- **Local misfit (G3).** `Misfit { samples, atoms, outside, fitted, worst }` from `compute_residuals` (a ratio > 1 and finite; NaN is never in M; never persisted). Trust row `sim::TrustKey::Misfit` (fails when |M| > `QUARANTINE_MAX_FRACTION` × fitted — a separate count from the held cap; `misfit_exceeds`). `EnergyResidual`/`ForceResidual` are judged outside M. Refusal `TeachRule::NearMisfit` (code 23) when any atom is within `QUARANTINE_FRACTION` × `max_descriptor_distance` of a same-species misfit atom; `atom_verdicts` marks it per atom; the fence stands only while |M| is within its limit (`misfit_fence`, `misfit_fence_stands`). Answers near M take `TeachOutcome::MisfitDisagrees` unless they agree, and agreeing ones are thinned and deduped. The knowledge map leaves M out.
- **The class rule and M** (`trust.rs` `compute_class_loo_full`, `LooSums`). M stays in the leave-one-out force and energy RMS and is left out of `force_max`/`energy_max`, worst/blockers, n_k and ā_c; q_k counts every fitted sample. `sim::ClassKey::EnergyRms` refuses a class or key whose energy RMS exceeds 1 when an M sample contributes to it (`calibrate::energy_rms_fails`; with M empty no verdict changes).
- Tests: `providers` `surrogate::tests` (`a_small_misfit_leaves_the_model_trusted`, `a_large_misfit_untrusts_the_model`, `a_gross_misfit_refuses_its_key`, `a_gross_energy_misfit_refuses_its_key`, `an_energy_rms_without_misfits_decides_nothing`, `a_geometry_near_a_misfit_is_refused_and_far_ones_answer`, …); the `#[ignore]`d acceptance `surrogate::tests::residual_diag::acceptance_on_the_collection` (`COLLECTION_DIR` = a copy of a collection; ≈ 5–6 min) and the cost measurement `refit_cost::refit_cost_on_a_collection` (`REFIT_COST=d4,s4`).

## SCF stall stop

- SCF stall stop (both solvers, `qm::scf` module doc "The stall stop"): a solve whose best Δρ has not halved within `ScfSettings::stall_window` = `qm::SCF_STALL_WINDOW` = 50 iterations, while that best is still ≥ `qm::SCF_STALL_LEVEL_PER_ELECTRON` (1e-3) × the electrons the solve carries (the level gate: stretched H₂ converges after 150-iteration plateaus far below it), ends with `QmError::ScfStalled` / `SolverError::ScfStalled` (a warm one is retried cold like `ScfNotConverged`, R15); checked after the convergence test, so converged results are bitwise unchanged. W's measurement: `cargo test -p providers --release scf_stall_measurement -- --ignored --nocapture`, `references.md` "SCF stall stop". `scf_observed` / `GpuSolver::solve_observed` feed `ActivityProbe::scf_iteration` (Δρ, the Harris–Foulkes energy, the countdown; on the GPU it rides on the Δρ readback); the Activity tab words a pass as **samples** ("Sample 42 of 158") and SCF rounds as **iterations** ("iteration 37 / 200"), and the solve log shows each solve's iterations and end (converged / stalled / cap). In a pass a stretched scan point that fails skips its scan's further-out points.
