## Releasing

Until 2026-11-20 a release was built by GitHub Actions from a pushed tag (`.github/workflows/release.yml`; installer spec `docs/superpowers/specs/2026-11-12-installer-updater-design.md`, plan Task 6) and came out as a **draft**. Claude never pushes a tag or publishes a release without asking the user first, and never handles the signing secret.

**Since 2026-11-20 (user decision) releases are built and signed locally**, and the workflow's tag trigger is off (restore `push: tags: ['v*']` to go back; it stays a build-only check through `workflow_dispatch`). The workflow's `MINISIGN_PASSWORD` secret did not unlock the key at v0.2.0-beta.3/4, so re-set it before using CI signing again. The local release:

1. Bump `[workspace.package] version` in `Cargo.toml`, run `cargo update -w --offline`, and commit both on `main`. Push, then (after asking the user) tag that commit with `git tag vX.Y.Z[-beta.N]` and `git push origin <tag>`.
2. On that commit with a clean tree: `cargo build -p app --release`, then `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\package.ps1 -RequireInstaller`, then `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\release-assets.ps1 -Version <ver>`, which writes `dist\SHA256SUMS.txt` and `dist\manifest.json`.
3. **The user signs** (Claude never handles the key or its password): `minisign -S -H -s <path to release-key.sec> -m D:\Projects\Physics\dist\SHA256SUMS.txt -t "atomic-sandbox <tag>"`. Never pipe the password from PowerShell: minisign 0.12 on Windows refuses a correct piped password (fixed in the workflow in cd0527aa).

- **When to bump `SCENE_FORMAT` and `PROFILE_FORMAT`.** These two are code-only numbers (scene files and profiles carry no version line, because an older parser refuses unknown lines), recorded in each release's `manifest.json` under `formats`, so a downgrade across a bump warns by type. Bump `crate::scene::SCENE_FORMAT` (`crates/app/src/scene.rs`) when a scene file this build writes would not parse in the previous release, or would mean something else there: a new line or field, a changed meaning or unit. Adding a reader for an older form does not bump it. Bump `crate::ui::profile::PROFILE_FORMAT` (`crates/app/src/ui/profile.rs`) when a profile this build writes would lose or change settings in the previous release: a renamed or re-meant key, a changed value grammar (`layout`, `hidden`, `window`). A new key alone does not bump it, since older builds skip unknown keys. Every other format number (`collection`, `sidecar`, `history`, `replay`, `pseudo_cache`, `checkpoint`) is read from its real version constant (`app::update::formats`) and moves only when that constant does. So a new persisted code or field inside an existing format (a new quarantine code in the sidecar, a new record field in a collection) needs that format's version bumped too, or the downgrade warnings can't see it.
- **Hidden flags** (for the installer and the release workflow, not for users):
  - `--write-manifest <path>`: writes this build's `manifest.json` (version, channel, data formats, no assets; `update::write_manifest`) and exits. The release workflow runs it on the shipped exe and fills in the assets.
  - `--write-icon <path>`: writes the app's `.ico` (the one `build.rs` embeds) and exits; `scripts\package.ps1` uses it for the installer's own icon.
  - `--resume-session <file>`: the installer's relaunch after an update. Opens the session scene saved before the hand-off (`<root>\updates\session.scene`, `update::apply::Session`) paused, in the window only.
  - `--update-failed`: added by the installer when a silent update got past its wait but failed; the status line says the installed files may be mixed (`main::UPDATE_FAILED`).

- **The `branch_jump` guard** (`providers::branch_jump`, spec §6.3; plan Task 8): replaces the shared-shell rule's occupation-pattern watch as the refusal to train on a step whose E(R) jumped. `CpuKs`/`GpuKs` each hold a `BranchJumpGuard` and judge every successful evaluation against their own previous one: ΔF = E₁ − E₀ against the trapezoid work W = −½Σ(F₀ + F₁)·ΔR; flagged when m = |ΔF − W| > b = 3(√(σ_E,0² + σ_E,1²) + ½‖ΔR‖√(σ_F,0² + σ_F,1²)) + 3κ_max‖ΔR‖³ (each evaluation's own tier; κ_max = 1 Ha/Bohr³ always — the first build's running median of m/‖ΔR‖³ was biased low on bond formation and locked in, Task 8 review C1). Pre-registered constants, never loosened: `BRANCH_JUMP_SIGMAS` 3, `BRANCH_JUMP_REACH` 0.1 Bohr, `KAPPA_MAX` 1. With N atoms each moving δ, b ≈ 3κ_max·N^{3/2}·δ³ + n: a 12 mHa jump is not detectable on a step that moves three or more atoms near the reach (review I2). Judged only when species, atom count, cell and origin match the previous evaluation (any difference restarts) and no atom moved more than 0.1 Bohr; `reset` (every edit) and a grid change forget it. A flagged step carries `EvalStats::branch_jump = Some(m)`, the warning `sim::branch_jump_warning(m)` ("F changed by 12.0 mHa more than the forces' work: the SCF moved to another stationary state (not trained on)") and `untrainable() == Some(BRANCH_JUMP_WARNING)` (after core overlaps; the old `occupation_changed` went in Task 9). The "not kept" notes cite each reason's section (`sim::untrainable_citation`: "spec §5.6" for core overlaps, "Fermi–Dirac spec §6.3" for a branch jump). With N↑ = N↓ a judged step reports `EvalStats::spin_change` = |Δ∫|ρ↑ − ρ↓|| (CPU `qm::orbitals::spin_summary`, GPU `GpuSolver::spin_abs_integral`).

## A failed GPU (gpu-fault fix, 2026-11-21)

- `gpu::GpuContext` installs an uncaptured-error handler and a device-lost callback on its device (`gpu::health`): both only record the first failure in `GpuContext::health` (`GpuHealth`), shared by every clone; `GpuContext::failure()` reads it after one non-blocking poll (which delivers the lost callback of a destroyed device). wgpu's default handler panicked on the calling thread; after a loss wgpu drops later errors silently (`ErrorType::DeviceLost`) and the next `create_buffer_init` panics on its invalid mapping. The viewer's Validation scopes (resize, pop-out, detached) still catch their own errors first.
- `GpuKs` (`providers::ks`, "A failed GPU") checks the record before and after every evaluation, Harris solve and orbital refresh: failed → `SolverError::GpuFailed(cause)` (never retried as "GPU busy"), its solver and display state dropped; a panic inside a solve while the device has failed is that failure. `ForceProvider::device_failure()` reports it (the surrogate: its latch or its teacher's); `Dynamics::tick` checks it first (its first statement, before the share tables and the orbital view; review A-M3) and pauses with `sim::gpu_failed_text(cause)` in `last_error` (it starts with `sim::GPU_FAILED_MESSAGE`; the next sentence follows `gpu::FailureKind::of(cause)`: out of memory / device lost (a driver reset or out of memory) / destroyed / another error "not known to be a memory problem"; then restart, and only if it recurs lower GPU memory or choose Balanced — never "out of memory" for a validation error), ending a pass or relax; Play/Step do not clear it. The bond references are dropped with it (the queue, a running side-solver job aborted, the side solver; none queued again), and `DynSnapshot::gpu_failed` is set.
- Nothing stays in flight (review A-I1): after a failure (latched, or the stepping teacher's device reporting it: `SurrogateKs::gpu_down`) `request_display`, `queue_harris`, `request_atom_density`, `request_atom_reference` refuse, `pump_side_queue` drops the queue (`drop_side_queue`: the references asked for answered once with "the GPU failed (cause)"), and `side_job_in_flight` is false; the worker skips its cloud, side-charge, orbital-retry and Harris jobs when `snap.gpu_failed` and resets the Harris schedule, so with `bonds_pending` empty it blocks on its inbox (tests `a_failed_gpu_leaves_the_worker_idle`, `a_failed_gpu_leaves_no_bond_reference_pending`, `after_a_gpu_failure_no_job_is_sent_to_the_auditor`, `a_failed_stepping_teacher_stops_the_side_jobs_before_any_answer`).

## SCF stall stop

- SCF stall stop (both solvers, `qm::scf` module doc "The stall stop"): a solve whose best Δρ has not halved within `ScfSettings::stall_window` = `qm::SCF_STALL_WINDOW` = 50 iterations, while that best is still ≥ `qm::SCF_STALL_LEVEL_PER_ELECTRON` (1e-3) × the electrons the solve carries (the level gate: stretched H₂ converges after 150-iteration plateaus far below it), ends with `QmError::ScfStalled` / `SolverError::ScfStalled` (a warm one is retried cold like `ScfNotConverged`, R15); checked after the convergence test, so converged results are bitwise unchanged. W's measurement: `cargo test -p providers --release scf_stall_measurement -- --ignored --nocapture`, `references.md` "SCF stall stop". `scf_observed` / `GpuSolver::solve_observed` feed `ActivityProbe::scf_iteration` (Δρ, the Harris–Foulkes energy, the countdown; on the GPU it rides on the Δρ readback); the Activity tab words a pass as **samples** ("Sample 42 of 158") and SCF rounds as **iterations** ("iteration 37 / 200"), and the solve log shows each solve's iterations and end (converged / stalled / cap). In a pass a stretched scan point that fails skips its scan's further-out points. Since the Fermi–Dirac switch (plan 2026-11-13 Task 9) no providers solve restarts the watch mid-solve: the release restart was the shared-shell rule's phase 2, deleted with `StallWatch::restart` in Task 10; FD converges in one phase.
